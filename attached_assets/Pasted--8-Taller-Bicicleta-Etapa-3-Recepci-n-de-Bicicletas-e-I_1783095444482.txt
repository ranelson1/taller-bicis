#8 - Taller Bicicleta — Etapa 3: Recepción de Bicicletas e Inspección Visual

## Contexto

Ya están implementadas:

- Etapa 0: setup, layout, login, navegación, base de datos y seed.
- Etapa 1: CRUDs maestros de usuarios/mecánicos, clientes, bicicletas, servicios, checklist de servicios, repuestos, categorías y métodos de pago.
- Etapa 2: módulo completo de presupuestos con ítems, versiones, timeline, aprobación/rechazo de ítems, resumen para cliente y estado “Listo para orden de trabajo”.

Ahora necesitamos implementar la Etapa 3: recepción de bicicletas e inspección visual.

Esta etapa conecta el presupuesto con la realidad física del taller. En la operación real hay dos escenarios:

1. Cliente pidió presupuesto antes por WhatsApp/llamada/Instagram/presencial, luego entrega la bicicleta.
2. Cliente llega directamente al taller y deja la bicicleta sin presupuesto previo.

En ambos casos, el taller debe poder registrar la recepción, inspeccionar la bicicleta y agregar hallazgos. Si durante la inspección aparecen trabajos adicionales, deben poder agregarse al presupuesto vigente como ítems pendientes de aprobación.

IMPORTANTE:
No implementar todavía órdenes de trabajo reales. Esta etapa termina con una bicicleta recibida, inspeccionada y con presupuesto actualizado si corresponde.

## Objetivo

Implementar el módulo de recepciones e inspección visual para que el taller pueda:

- Registrar la recepción física de una bicicleta.
- Asociar la recepción a un cliente.
- Asociar la recepción a una bicicleta.
- Asociar opcionalmente la recepción a un presupuesto existente.
- Registrar problema reportado por el cliente.
- Registrar estado visual inicial.
- Registrar accesorios recibidos.
- Registrar inspección visual.
- Registrar hallazgos.
- Crear ítems adicionales en un presupuesto desde hallazgos de inspección.
- Marcar esos adicionales como pendientes de aprobación.
- Ver timeline de recepción e inspección.
- Ver en el presupuesto los adicionales creados desde inspección visual.

## Alcance incluido

### 1. Recepciones

Crear módulo de recepciones.

Rutas frontend:

- `/recepciones`
- `/recepciones/nueva`
- `/recepciones/:id`

La recepción debe poder crearse desde:

- Menú principal “Recepciones”.
- Presupuesto existente, con botón “Registrar recepción”.
- Cliente/bicicleta existente, si es simple de implementar.

Campos de recepción:

- Código automático tipo `R-0001`, `R-0002`, etc.
- Cliente obligatorio.
- Bicicleta obligatoria.
- Presupuesto asociado opcional.
- Usuario que recibe.
- Fecha y hora de recepción.
- Problema reportado por cliente.
- Estado visual inicial.
- Accesorios recibidos.
- Notas internas.
- Notas visibles para cliente.
- Estado de recepción.
- Activo/inactivo.
- created_at.
- updated_at.

Estados de recepción:

- `received` → Recibida
- `in_inspection` → En inspección
- `inspection_completed` → Inspección completada
- `waiting_quote_approval` → Esperando aprobación de presupuesto
- `ready_for_work_order` → Lista para orden de trabajo
- `cancelled` → Cancelada

Reglas:

- Una recepción siempre debe tener cliente y bicicleta.
- Puede tener o no tener presupuesto asociado.
- Si viene desde un presupuesto, debe quedar vinculada al presupuesto.
- Si no tiene presupuesto, debe permitir crear uno desde la recepción en base al cliente, bicicleta y problema reportado.
- No crear OT real todavía.

La inspección debe permitir registrar múltiples hallazgos.

Campos de inspección / hallazgo:

- Recepción asociada.
- Presupuesto asociado opcional.
- Mecánico que inspecciona.
- Fecha.
- Área/sistema revisado.
- Hallazgo.
- Severidad.
- Recomendación.
- Crear ítem adicional en presupuesto: sí/no.
- Tipo de ítem sugerido.
- Servicio asociado opcional.
- Repuesto asociado opcional.
- Descripción para presupuesto.
- Cantidad.
- Precio unitario.
- Horas hombre estimadas.
- Estado de aprobación del adicional.
- Notas internas.
- created_at.
- updated_at.

Áreas/sistemas sugeridos:

- Suspensión
- Frenos
- Transmisión
- Ruedas
- Neumáticos
- Cuadro
- Dirección
- Motor/e-bike
- Dropper
- Otro

Severidad:

- `low` → Baja
- `medium` → Media
- `high` → Alta
- `critical` → Crítica

### 4. Adicionales desde inspección

Desde un hallazgo de inspección, el usuario debe poder crear un ítem adicional en el presupuesto asociado.

Reglas:

- Si la recepción tiene presupuesto asociado, el adicional se agrega a ese presupuesto.
- El ítem creado debe quedar con:
  - `origin = visual_inspection`
  - `approval_status = pending`
  - `item_type` según lo seleccionado
  - `description` desde la recomendación/hallazgo
  - `quantity`, `unit_price`, `total`, `estimated_labor_hours`
  - `service_id` si viene desde un servicio
  - `part_id` si viene desde un repuesto

- Si el presupuesto ya estaba enviado, aprobado o aprobado parcialmente, al agregar un adicional debe cambiar a estado:
  - `updated_after_sent`

- No generar nueva versión automáticamente al crear el adicional.
- La nueva versión debe generarse cuando el presupuesto se vuelva a marcar como “Enviado al cliente”, respetando la lógica ya implementada en Etapa 2.
- Registrar evento en timeline del presupuesto:
  - “Se agregó adicional desde inspección visual”.

### 5. Crear presupuesto desde recepción

Cuando una recepción no tenga presupuesto asociado, debe existir una acción:

- “Crear presupuesto desde recepción”

Esta acción debe:

- Crear un presupuesto en estado `draft`.
- Asociarlo al cliente y bicicleta de la recepción.
- Usar como `initial_requirement` el problema reportado por el cliente.
- Asociar el presupuesto creado a la recepción.
- Redirigir al detalle del presupuesto o permitir volver a la recepción.

No implementar lógica de OT.

### 6. Timeline

Usar la tabla `timeline_events` ya existente si es posible.

Registrar eventos para:

- Recepción creada.
- Recepción editada.
- Estado de recepción cambiado.
- Inspección iniciada.
- Hallazgo agregado.
- Hallazgo editado.
- Hallazgo marcado como adicional de presupuesto.
- Presupuesto creado desde recepción.
- Recepción lista para orden de trabajo.

El detalle de recepción debe mostrar un timeline propio.

Si `timeline_events` ya funciona con `entity_type` y `entity_id`, usar:

- `entity_type = reception`
- `entity_type = inspection`
- `entity_type = quote`, cuando el evento afecte presupuesto.

### 7. Relación con presupuestos

Actualizar el detalle de presupuesto para mostrar, si existe:

- Recepción asociada.
- Estado de recepción.
- Link a la recepción.
- Hallazgos de inspección asociados al presupuesto, si aplica.
- Ítems cuyo origen sea inspección visual.

Agregar botón en detalle de presupuesto:

- “Registrar recepción”

Este botón debe crear o llevar a una recepción asociada al presupuesto.

Regla:
Un presupuesto puede estar asociado a una recepción, pero no todos los presupuestos tienen recepción todavía.
